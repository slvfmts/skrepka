# Как Google Docs API ведёт себя с комментариями

Файл для разработчиков и для тех, кто хочет перепроверить заявления проекта.

Здесь выжимка эмпирики, на которой построена skrepka: что происходит с комментариями и стилями при программной правке Google Документа. Каждый пункт проверен на живом API, не только по документации. Публикуем, потому что связного описания этого поведения в открытых источниках почти нет.

Оговорка: это наблюдаемое поведение на момент проверки (2026), а не контракт Google. Оно может измениться. Идентификаторы тестовых документов сюда не входят.

## Три способа поменять текст и что они делают с комментариями

| Операция | Комментарии | Вывод |
|----------|-------------|-------|
| `drive.files.update` (перезалив media) | Убивает. Якоря `kix.*` ломаются, треды становятся «призраками»: живы в API (`deleted=false`), но невидимы в интерфейсе. | Никогда не использовать для правки текста с комментами. |
| `deleteContentRange` + `insertText` | Ломает текст, если диапазон удаления пересекает якорь. Google сдвигает/обрезает удаление, «защищая» якорь, — получаются частичные удаления и мусорные фрагменты. | Тот же батч на том же тексте без комментов работает, с комментами — портит. |
| `replaceAllText` | Сохраняет. Единственный подтверждённый способ менять текст, не ломая якоря. | На нём построены все правки skrepka. |
| `insertText` рядом с якорем | Безопасно. Вставка вплотную к любой границе живого якоря — якорь жив, текст цел. | Ничего не удаляет. |

## Полное покрытие якоря убивает тред, а частичное нет

`replaceAllText`, чей матч целиком накрывает якорь живого комментария, превращает его в призрак (исчезает из UI и из экспорта, в API остаётся жив). Текст при этом заменяется корректно, порчи нет, но тред потерян.

Частичное перекрытие безопасно: якорь сжимается до уцелевшего текста. Практическое наблюдение: якорь может «переехать» на хвост замены, а не строго на исходные уцелевшие символы, но тред остаётся живым. Если не уцелело ни одного символа, тред умирает. Отсюда правило skrepka: замену, полностью покрывающую якорь, отклонять, а пользователю подсказывать разбить её на две так, чтобы хотя бы один исходный символ якоря уцелел (повтор того же текста в замене не помогает, важен именно уцелевший оригинал).

## Экспорт документа как детектор живых якорей

Позиции якорей комментариев через публичный API не наблюдаемы. Но экспорт документа в HTML или DOCX их показывает:

- DOCX-экспорт даёт точные границы: `commentRangeStart … текст … commentRangeEnd` вокруг якорного текста. Это доступная в GA замена anchor-ranges из Developer Preview.
- Призраки в экспорт не попадают вовсе. На документе с несколькими якорными комментами в `word/comments.xml` оказываются только живые треды (и реплаи).
- Поэтому «коммент-призрак» и «экспорт протух» по одному экспорту неразличимы. Единственная надёжная политика для перезаписей — поимённый учёт: каждый не-удалённый якорный коммент обязан найтись в экспорте, иначе замены и удаления блокируются целиком.
- Ключ сопоставления API ↔ DOCX: `(автор, createdTime, усечённое до секунд)`. `w:date` в экспорте это `createdTime`, обрезанный (не округлённый) до секунды. `quotedFileContent` для сопоставления непригоден, это устаревший снапшот момента создания, который на живом документе уже не совпадает с текущим текстом.
- Реплаи экспортируются отдельными записями со своими диапазонами, дублирующими диапазон родителя. Для защиты от перекрытий это безвредная избыточность.

## Комментарии, созданные через API, не привязываются к тексту

`comments.create` с `anchor` + `quotedFileContent` создаёт коммент, который в интерфейсе отображается как document-level, а не как привязанный к тексту. Настоящие якоря имеют только комментарии, созданные в интерфейсе. Как следствие, фикстуры с реальными якорями нельзя нагенерировать через API, только руками в UI. И `files.copy` не копирует комментарии: бэкап перед деструктивным обновлением не спасает треды, и текст `--acknowledge-loss` об этом предупреждает.

## Резолв только через replies

Поле «resolved» доступно только на чтение. Зарезолвить тред можно исключительно через `replies.create` с `action: "resolve"`. skrepka делает это только по явному подтверждению человека, агент не резолвит сам.

## Гонки при записи

Создание комментария меняет `revisionId` документа. Поэтому обязательный `writeControl.requiredRevisionId` на каждом `batchUpdate` сам отбивает гонку «коммент появился между чтением и записью»: батч применяется целиком или падает на конфликте.

## Артефакты HTML-экспорта Google (и как их чистить)

- Часть обычных пробелов отдаётся как `&nbsp;`, нормализуем на границе документ↔markdown. Иначе `&nbsp;` на стыке инлайн-тегов «съедает» пробел (`<b>слово</b><b>&nbsp;жирным</b>` → в markdown пробел исчезает).
- Ссылки завёрнуты в редирект `google.com/url?q=…` (иногда вложенный), разворачиваем.
- Жирный/курсив приходят как CSS (`font-weight:700` / `font-style:italic`) на `span`, а не как теги, конвертируем в `<b>/<i>` до `markdownify`, иначе стили теряются и следующая синхронизация срежет их и в документе (замкнутая петля).
- HTML-экспорт комментированного документа вшивает в тело сами комментарии (инлайн-маркеры `[a]` и хвостовые блоки текстов), их нужно вырезать по строгим паттернам, иначе локальная копия обрастает мусором.

## Стили при полной перезаписи абзаца

- Абзацные свойства выживают при перезаписи текста внутри абзаца (символ переноса строки не трогается): выравнивание, отступы, межстрочный интервал, фон.
- Убивает стили собственный style-pass: установка `namedStyleType` сбрасывает остальные свойства абзаца к дефолтам стиля (это документированная семантика, `namedStyleType` применяется первым в запросе). Лечение: слать сохраняемые поля в том же запросе `updateParagraphStyle`.
- Текстовый стиль нового текста не наследуется надёжно, его нужно захватить до перезаписи и переприменить полной маской. Однородный стиль восстанавливается; неоднородное внутриабзацное оформление детерминированно очищается и репортится полем `inline_styles_dropped`.
- Снятие ссылки это двойной подвох: `{"link": None}` в теле молча выбрасывается клиентом, а unset через маску срабатывает только если весь диапазон запроса целиком является ссылкой.

## Прочее

- UTF-16. Смещения Docs API считаются в кодовых единицах UTF-16: символы вне BMP (эмодзи и т.п.) занимают две единицы. Наивный посимвольный маппинг ломается на них.
- Developer Preview anchor-ranges недоступны без отдельного enrollment: параметр `commentsViewMode` в прото есть, но валидные значения не отдаются и в discovery отсутствуют, в v1 считаем возможность недоступной и опираемся на экспорт-детектор.
