# Ограничения актуальной версии

**`replace_anchor` (#52) mapping boundary.** Duplicate ordinal mapping uses
only readable top-level paragraphs in the proven tab segment whose text exactly
matches the fresh DOCX marker `para_text`; title/table/non-twin elements and
flattened nested-table paragraphs cannot shift the selected candidate. The
enumerated exact-match count must equal the API candidate count, otherwise the
operation refuses before semantic write. Identical root/reply descriptors are
deduped, while a descriptor from another thread on the selected range keeps the
aggregated fence. `with: ""` intentionally remains fail-closed because deleting
the entire anchor can orphan its thread.

**Advisory `patch --dry-run` (#50).** Сухой прогон читает один snapshot Docs и
comments census и не отправляет `batchUpdate`, replies/deletes, canary или DOCX
export. На чистом документе разрешимые index/suggestion/TOC/schema gates могут
дать `would_apply` или `would_refuse`; no-op получает `noop`. На документе с
якорями destructive/freshness-dependent правка получает
`unknown: fresh_anchor_map_requires_canary`, а последующие зависящие операции
получают `not_simulated` с `depends_on`. Это bounded advisory, не sequential
simulator и не обещание, что живой anchor-map останется свежим. Receipt всегда
имеет `action=dry-run`, `writes_performed=0`; exit 0 только для `would_apply` и
`noop`, иначе 3.
Явный `--tab` с повторяющимся `tabId` не выбирает первую вкладку: dry-run
возвращает `would_refuse` с bounded `duplicate_tab_id` candidates/count.

**Диагностика отказов C1 и `sync` (#51).** Когда замена полностью накрывает
последний живой anchor, отказ включает bounded UTF-16 ranges для anchor,
исходной правки и попытки сужения, а также видимые общий префикс/суффикс.
`replace_anchor` (точный `comment_id`) рекламируется только для применимой
anchor-only geometry; `replace_around_anchor` — только для явной схемы с exact
outer quote/extents и новым anchor. Cross-paragraph, TOC, named-range,
control-character и grapheme отказы называют split/UI recovery и не обещают
эти команды. Для обычной правки окружение anchor оставляют дословным и
выносят соседние слова в отдельные операции. Не следует обещать `occurrence`
для повторяющегося комментируемого абзаца.

Оставшийся hard guard `sync` на неоднозначной кратности близнецов показывает
bounded quote samples, sampled positions, counts и SHA-256. Большие позиции и
полный текст не печатаются. Публичный deferred receipt также ограничивает
каждый scalar и динамический ключ (включая вложенные composite keys), а для
усечённых списков сохраняет count/SHA-256 полного canonical набора. Полные
данные остаются только в recovery journal. Если сработал уже существующий r15
`duplicate-ambiguity`, безопасный hull откладывается, а не превращается в этот
старый отказ; диагностика относится только к остаточному guard.

**Deferred raw/Markdown blocks (r15).** Во всех composite, crossing-pins,
cost-limit, duplicate-ambiguity и protected-fence hulls материализация после
canary закрыта одним правилом: ровно один raw-verbatim block должен быть
поддержан downstream. Parse note не является разрешением для image, HTML,
или другого `opaque-md` raw block — такой hull отказывается без semantic
write. Canary cleanup выполняется до отказа; если cleanup не доказан, receipt
содержит literal canary и ручной recovery.

**`replace_around_anchor` (#33).** Для внешнего диапазона, который строго
содержит живой anchor, операция требует exact witness `quote`, точный `comment_id`
и обязательный новый fragment descriptor:

```json
{"op":"replace_around_anchor", "comment_id":"c1",
 "quote":"старый внешний фрагмент", "with":"новый внешний фрагмент",
 "before_utf16":4, "after_utf16":5,
 "anchor":{"text":"новый текст anchor", "start_utf16":7}}
```

`before_utf16`/`after_utf16` вычисляют диапазон относительно свежего marker;
`quote` — exact witness этого диапазона, а не глобально уникальная цитата.
Оба extent неотрицательны, и хотя бы один положителен. `anchor.text` выбирается в `with` только по указанному UTF-16 offset; пустой или
попадающий внутрь surrogate pair fragment отклоняется. Старый anchor не берётся
из `quotedFileContent`: он доказывается свежим DOCX marker через путь #52. Один
revision-pinned batch сначала выполняет proven anchor rewrite, затем меняет
правую и левую части за его границами. Любой соседний anchor, ambiguous/foreign
fence, suggestion, named/protected range, неверный extent/witness или race
даёт bounded отказ до semantic write. Disposable API/DOCX positive split
пройден до финального relative-schema hardening; exact current extents покрыты
offline, UI survival глазами остаётся отдельным acceptance gate. Старый
однокодпоинтовый anchor (включая одиночный emoji) намеренно отказывается до
semantic write: существующий proven rewrite требует внутреннюю границу, которой
у него нет; такой случай правится в UI.

Если `quote` и `with` побайтно совпадают, no-op разрешён только когда
`anchor.start_utf16 == fresh_marker_start - outer_start` и `anchor.text` точно
совпадает с marker: одинаковый текст в другой позиции не считается no-op и
отказывается bounded. После marker/quote/fragment/suggestion freshness gates
такой no-op проходит до style/named/foreign deletion-only fences и делает
только canary cleanup; оставшийся protected/ambiguous fence всегда блокирует,
при cleanup ошибке receipt обязан назвать
literal canary и ручное recovery. Это не отменяет общие suggestions/race gates.
Guard для старого anchor из одного code point (ASCII или emoji) применяется
до этого no-op shortcut: такой вызов также bounded-refuse без semantic write.

**`replace_anchor` (#52).** Эта операция адресует ровно один корневой
активный тред по `comment_id` и берёт диапазон только из свежего DOCX marker,
полученного после canary. Старая `quotedFileContent`, occurrence и поиск
одинакового текста не являются источником координат. Вкладка root/child и
revision закрепляются тем же snapshot/census; неизвестный, ghost, resolved,
недоступный, неоднозначный или malformed marker даёт отказ до смысловой
записи. Дубликаты видимого текста допустимы, если marker и порядок top-level
paragraph elements однозначно сопоставлены; paragraphs nested в таблицах не
сдвигают этот ordinal. Идентичные marker descriptors root/reply одного
треда дедуплицируются, но разные ranges остаются отказом. Пересечение
suggestion, другого живого якоря или named range остаётся защищённым; при
агрегированном ambiguous fence его ownership проверяется структурно по
comment_id, а не по тексту label. Пустая замена отказывается: удаление всех
символов осиротит тред, и безопасного результата для неё нет.

**Повторяющиеся цитаты в `mark`.** Если цитата встречается один раз,
`mark` выбирает её и без `--occurrence`. При двух и более совпадениях флаг
обязателен: команда не угадывает первое вхождение. Можно явно указать любое
`--occurrence N` в диапазоне `1..N` (включая `1`); нулевые, отрицательные и
выходящие за границы значения отклоняются до записи.

Если правку нельзя внести безопасно, skrepka откажет — молча испортить документ она не может. Отказ при этом всегда стоит человеку дороже, чем кажется, поэтому с версии 0.10 skrepka сначала пробует сделать правку иначе и отказывает только по конкретной операции, а не по документу целиком. Ниже то, чего она не делает. Почему так устроено, разобрано в [FINDINGS.md](FINDINGS.md).

**Дубликаты текста в `replace_range`.** Именованный диапазон в
`replace_range` адресуется по индексам даже на документе с живыми якорными
комментариями; одинаковый текст в другом месте не является причиной отказа и
не переписывается. Это не означает ослабления ограды: перед записью нужен
свежий canary/export snapshot, а целевой диапазон не может пересекать живой
или невидимый заблокированный якорь, suggestion либо другой named range.
Разрешённый тред с якорем делает прямую индексную замену недоказуемой и потому
отказывается fail-closed. Целевой tab и revision закрепляются в одном батче;
после 5xx состояние определяется существующей canary-семантикой, а не
повторяется вслепую.
Для индексной замены имя должно однозначно указывать на один объект Google
с непустым `namedRangeId` и одним contiguous-диапазоном. Несколько объектов
под одним именем (даже если их диапазоны стыкуются), пропавший ID или смена
ID/границ между начальным и fresh snapshot дают отказ до canary.

## Структура документа

**Таблицы.** skrepka не редактирует структуру таблиц: не добавляет и не удаляет строки и столбцы, не меняет саму сетку. Текст внутри ячейки править умеет, поиск по цитате заходит в ячейки, но перестройку таблицы делайте руками в интерфейсе Google Docs. Для команды `sync` таблица целиком считается неделимой: если вы поменяли таблицу в локальном файле, синхронизация остановится и попросит перенести это изменение вручную.

**Вкладки (tabs).** `patch` работает во вкладках, в том числе когда в документе есть комментарии с привязкой к тексту: до версии 0.14 такой документ отказывался целиком. Целевую вкладку нужно назвать флагом `--tab <id>`; без него skrepka отказывает и печатает список вкладок с их названиями и идентификаторами. Сама она вкладку по правке пока не выбирает, и флаг принимает идентификатор, а не название.

Правка запирается во вкладке: одинаковый текст в соседних вкладках не меняется, комментарии соседних вкладок правку не блокируют и своей защиты не теряют. Перед тем как разместить якорь, skrepka доказывает границы целевой вкладки в выгрузке, сверяя содержимое элемент за элементом. Если доказать не удалось — например, абзац содержит смарт-чип или непринятое предложение, — замены в этой вкладке отклоняются с указанием места расхождения.

Команда `suggestions`, напротив, читает все корневые и дочерние вкладки сразу.
Каждый хунк подписан идентификатором и названием вкладки; если две preview-версии
вернули разный или дублирующийся набор `tabId`, команда просит повторить чтение и
не делает вывода «предложений нет».

`sync` по-прежнему работает только с одновкладочными документами: многовкладочный он отклонит и предложит редактировать в интерфейсе.

`comments` отдаёт треды всего документа одним плоским списком. Drive API не
сообщает вкладку, поэтому команда подписывает её только при узком проверяемом
условии: сохранённая `quotedFileContent` дословно встречается в теле ровно одной
корневой или дочерней вкладки текущего Docs-снимка. Тогда `tab_attribution.status`
равен `exact`. Несколько совпавших вкладок, ни одного совпадения, якорь без
цитаты и отсутствующий/дублирующийся `tabId` дают `unknown` с причиной и
кандидатами — первый кандидат не считается ответом. Комментарий без якоря и
цитаты помечен отдельно как `document`. Цитата является устаревающим снимком,
поэтому эта атрибуция служит для отбора при чтении, а не разрешает запись.

Запись заперта независимо и строже. В многовкладочном документе `reply` и
`resolve` требуют `--tab <id>`, доказывают по DOCX-якорю, что выбранный тред
находится именно в этой вкладке, и перед записью проверяют свежесть экспорта
canary-маркером. Чужая, неоднозначная или устаревшая привязка даёт отказ до
ответа. Комментарий уровня всего документа можно обработать без `--tab`; явно
приписать его вкладке команда не позволит. Фильтр по автору остаётся доступен
через `author.me`.

**Сноски.** Через skrepka сноски не переносятся и не редактируются. Работайте с ними в интерфейсе Google Docs.

**Вложенные списки.** Глубокая вложенность поддержана ограниченно: при полной перезаписи абзаца уровни вложенности могут сбиться.

**Мягкий перенос строки (Shift+Enter).** Работает во все стороны, с версии 0.15. Абзац с мягким переносом — заголовок и подзаголовок превью в одном абзаце — правится как обычный, в том числе когда на нём висит комментарий; до 0.15 один такой абзац закрывал замены во всём документе. Мягкий перенос можно поставить и правкой: он разрешён в тексте вставки и замены.

В markdown мягкий перенос записывается двумя пробелами на конце строки (или обратным слэшем) — так его понимает импорт при `upload`, и так же его пишет `download`. Круг замыкается без потерь, включая переносы внутри ячеек таблицы и в полужирном тексте. Обычный перенос строки в markdown по-прежнему склеивается в пробел — это поведение самого Google, и оно правильное: абзац в markdown можно переносить как угодно.

Чего мягкий перенос не умеет: `sync` считает абзац с ним неделимым и правку внутри такого абзаца не переносит — правьте его через `patch`.

**Разрыв страницы.** Абзац с разрывом страницы skrepka читает и комментарий в нём защищает, но адресовать правку через разрыв нельзя: цитата, пересекающая его, не найдётся. Правьте текст до и после разрыва по отдельности. В круге markdown разрыв страницы теряется — `download` пишет его горизонтальной чертой, и обратной загрузкой он не восстанавливается; там же теряется табуляция, она превращается в пробел. Разрыв колонки не поддержан вовсе: если он стоит в прокомментированном абзаце, замены в документе останавливаются.

## Комментарии

**Замена, которая целиком накрывает текст с комментарием.** Работает, комментарий остаётся. skrepka пробует три пути по очереди. Если вы поменяли в предложении одно слово, замена сужается до этого слова, и якорь комментария не задет вовсе. Если замена только дописывает текст и ничего не удаляет, она выполняется как вставка. А если меняется весь прокомментированный фрагмент без остатка — skrepka делает ровно то, что человек делает руками: вписывает новый текст внутрь выделения, к которому привязан комментарий, и убирает старый, одной неделимой операцией. Комментарий после этого висит на новом тексте, которого не видел, когда его писали, — для сценария «заказчик прокомментировал абзац, редактор переписал абзац» так и надо, и в ответе это сказано прямо.

Перезапись не сработает, если якорь задевает соседний комментарий или именованный диапазон, если в тексте замены есть перевод строки или табуляция, или если комментарий висит на куске внутри заменяемого, а не на нём целиком. Мягкий перенос в тексте такой замены разрешён — он не создаёт абзаца и счёт позиций не ломает; перевод строки создаёт, поэтому его здесь нельзя, хотя в обычной правке можно. Разницу отказ называет вслух. Во всех этих случаях остаётся прежний отказ со ссылкой на тред. Закрытые треды перезаписи больше не мешают: до 0.12 один закрытый тред в любом углу документа выключал её во всём файле.

Оглавление само по себе перезапись больше не блокирует. Его текст skrepka не адресует как цель правки, но считает при проверке уникальности: если искомая или промежуточная строка повторяется в оглавлении, операция консервативно отказывается до записи. Трогает ли `replaceAllText` сгенерированный текст оглавления, пока не измерено; поэтому совпадение считается потенциальным, а не объявляется доказанным.

Есть ещё один отказ, и он про форму текста, а не про комментарии: перезапись не берётся за фрагмент, который кончается символом, неотделимым от предыдущего — буквой со знаком ударения, составным эмодзи из нескольких кодовых точек, флагом. Перезапись вставляет новый текст прямо перед последним символом, а внутрь такой пары Google вставить не даёт (замерено). Сдвиньте границу выделения на один символ или правьте фрагмент в интерфейсе. Обычное эмодзи в конце фразы этому не мешает и работает как раньше — включая документы с закрытыми тредами, где до 0.13 стояла отдельная гвардия.

**Перестановка блоков.** Переставить блоки по документу skrepka умеет: скачайте файл командой `download`, поменяйте порядок в нём и залейте обратно через `sync`. Оформление, которого markdown не выражает — цвет, подсветка, кегль, — переезжает вместе с блоком; в отчёте перестановка видна как `moved`. У `patch` операции переноса нет и не будет: он адресует правку цитатой, а переезд — это про порядок целых блоков.

Стена остаётся одна, и она не про инструмент: **сам блок, на котором висит живой
комментарий, переехать не может.** В Docs API нет запроса «переместить диапазон»,
перенос всегда раскладывается в «вставить копию на новом месте и удалить оригинал»,
а удаление оригинала схлопывает якорь и делает тред призраком. Пересоздать
комментарий на новом месте тоже нельзя — комментарии, созданные через API, к тексту
не привязываются.

Но это больше не означает автоматический отказ всей перестановке. `sync` закрепляет
прокомментированный блок и ищет равносильный план, в котором переезжает сосед. Если
несколько закреплённых блоков требуют несовместимого порядка, этот компонент
откладывается, а независимые безопасные правки применяются. Результат называется
`partially-synced` или `partial-noop`, завершается кодом 3 и остаётся в локальном
файле как неприменённое намерение; это не полный успех. Сам невозможный порядок
сделайте руками в интерфейсе и проверьте, что комментарии уцелели.

Частичность локализует пересекающиеся закреплённые блоки, составные якоря,
неоднозначную кратность дублей, named range / неразмещённый anchor / blocked
span и измеренный cost corridor. Невозможный компонент откладывается целиком,
включая обе половины переезда; независимые операции продолжаются.

Для чистой перестановки длиннее 20 блоков точный многокритериальный optimum не
доказывается. Вместо него строится детерминированное допустимое выравнивание
между обязательными anchor/opaque-барьерами, а receipt и журнал явно сообщают
`optimality_proven: false`. Стоимость всё равно локализуется по независимым
компонентам и ограничивается совокупно. Уже готовый фактический батч проверяется
по тем же жёстким пределам ещё раз: несоответствие расчёту остановит весь запуск
до записи как внутренняя страховка, а не будет выдано за частичный успех.

Отдельно замерено, что переезд СОСЕДЕЙ прокомментированному абзацу ничем не грозит: вставка целого абзаца хоть вплотную к началу якоря, хоть сразу за ним тред не рвёт и якорь не расширяет. Так что перестановка вокруг комментария — обычная работа, а не риск.

**Комментарий на нескольких фрагментах.** Тред умирает, только когда исчезает его последний фрагмент. Замена, накрывшая один из трёх, проходит.

**Комментарий, выделенный через границу абзаца.** Работает с 0.12 — например, комментарий к заголовку вместе с подзаголовком или к пункту списка вместе со следующим. Правку внутри такого фрагмента skrepka сузит до изменённого куска, и комментарий останется на месте. Не работает один случай: если абзац, в котором комментарий начинается или заканчивается, повторяется в документе дословно, определить, к какой копии он относится, нечем, и замены с удалениями останавливаются. Разводится тем же способом — измените одну из копий на одно слово. Раньше любое такое выделение запирало документ целиком.

**Комментарий, потерявший привязку («призрак»).** Комментарий, чей текст удалили или переписали в интерфейсе, остаётся в документе без привязки. Это нормальная практика, а не поломка, и с 0.12 такой тред работе не мешает: skrepka называет его в квитанции ссылкой и продолжает править документ. Убрать его может только человек — «Удалить» в панели комментариев; чужой комментарий инструмент не удаляет.

Признать тред призраком skrepka берётся не всегда. Нужно, чтобы сошлись два признака: в выгрузке документа есть комментарий, созданный позже **последней текущей записи** пропавшего треда (обычный ответ и служебные resolve/reopen тоже считаются), и текста, к которому пропавший был привязан, в документе больше нет. Если второй признак не сошёлся — старый текст ещё на месте, — это место отклоняется для правок, а остальной документ правится. Если не сошёлся первый — после последней активности треда нет более новой экспортной записи, и отличить отсутствие от запаздывающей выгрузки нечем, — замены и удаления останавливаются, как раньше. Практически это значит: подождите минуту и повторите команду либо ответьте в любой другой тред.

Тот же осторожный вердикт теперь виден заранее в выводе `comments`, полем
`anchor_export`. `status: ghost` означает, что оба признака сошлись;
`status: unknown` — что данных не хватило. `status: record_present` говорит
только о записи треда в прочитанной DOCX-выгрузке, а не о доказанно живом якоре
прямо сейчас: команда чтения не пишет canary, и потому рядом всегда стоит
`export_freshness: unproven`. Эта оговорка намеренная — stale-выгрузка может
показывать якорь до его исчезновения. Сбой экспорта не ломает список
комментариев, а переводит якорный статус в `unknown`.

Чтобы сам read-only вывод не склеил несовместимые состояния трёх API, `comments`
обрамляет DOCX-экспорт полным пагинированным чтением комментариев и двумя
чтениями Docs. Отпечаток комментариев и Docs revisionId должны совпасть; для
обычного view-only ответа без revisionId сравнивается канонический hash полного
Docs resource. При гонке весь проход повторяется один раз, после чего связанные
`anchor_export` и `tab_attribution` остаются `unknown` с причиной
`snapshot_changed_during_read`. Если только одна сторона вернула revisionId или
у DOCX-записи нельзя прочитать author/date, отсутствие также не объявляется
призраком. Все эти проверки состоят только из чтений: canary, ответов и других
записей команда `comments` не делает.

Из этого правила есть одно исключение, и оно снимает целый класс отказов. У треда, который никогда не был привязан к тексту, нет цитаты вовсе — так выглядит комментарий, оставленный через API любым другим инструментом. Если при этом в выгрузке документа **нет ни одной записи о комментариях** — а именно так выглядит документ, где все комментарии оставлены через API, — признак свежести молчал бы вечно, и раньше такой документ стоял запертым навсегда. Теперь он не требуется: терять такому треду нечего, настоящий якорь без цитаты бывает только на картинке, а комментарий на картинке в выгрузке есть и до этой ветки не доходит (замерено).

Исключение узкое: как только в выгрузке появляется хоть одна запись, признак свежести снова обязателен и для тредов без цитаты — раз дешёвое второе мнение доступно, оно используется.

**Документ с «осиротевшими» комментариями.** Если учёт комментариев не сходится по другой причине — например, документ правили сторонним инструментом, — skrepka остановит замены и удаления, пока это не будет разобрано. Вставки при этом работают всегда: они ничего не удаляют.

**Удалить можно только свой обычный ответ, а не тред.** Для лишнего ответа есть `skrepka unreply <doc> <comment_id> <reply_id>`; точные идентификаторы видны в полном выводе `comments`. Перед единственным `replies.delete` команда одним пагинированным чтением с удалёнными записями доказывает, что родительский тред жив и открыт, ответ принадлежит именно ему, ещё не удалён, не является действием `resolve`/`reopen`, а Google явно вернул `author.me: true`. Отсутствующее поле `me` считается неопределённостью и даёт отказ. Родительский комментарий, чужой ответ и системное действие команда не удаляет; для них recovery остаётся в интерфейсе Google Docs. Между чтением и удалением остаётся неизбежное окно гонки: Drive не даёт условного токена для `replies.delete`, но точные неизменяемые идентификаторы и автор ответа уже доказаны до вызова.

**Комментарий в таблице.** Обычный комментарий в ячейке ничему не мешает: skrepka видит, в какой именно ячейке он стоит, и правит текст в таблице так же, как в теле документа. Раньше один комментарий в ячейке делал нередактируемыми все таблицы файла.

Отказ остаётся там, где положение якоря внутри ячейки не читается, и он ограничен ячейкой, а не документом. Так бывает в двух случаях: в ячейке несколько дословно одинаковых абзацев; в ней есть абзац со смарт-чипом, текст которого API не отдаёт. Мягкий перенос в ячейке до 0.15 был третьим таким случаем — теперь комментарий в такой ячейке размещается точно. Отдельный случай — выделение, протянутое из одной ячейки в другую: такой комментарий skrepka не размещает точно и отклоняет правки во всей таблице, которая его держит. Во всех этих случаях остальной документ, включая другие ячейки той же таблицы, правится как обычно.

Есть и случай, когда skrepka останавливает замены во всём документе: если выгрузка и сам документ описывают таблицы по-разному — разное число таблиц, строк, колонок или разный текст в ячейке. Это значит, что два источника читают документ несогласованно, и тогда ни одна координата не заслуживает доверия: ячейка, на которую указывает такой адрес, может оказаться соседней, и ограда встала бы рядом с комментарием, а не вокруг него. На практике так бывает, если документ меняли между выгрузкой и чтением — повторите команду.

Структуру таблиц skrepka по-прежнему не меняет, и для `sync` таблица остаётся неделимой.

**Дословно повторяющийся абзац.** Если один и тот же абзац встречается в документе дважды слово в слово, определить, к какой из копий относится комментарий, нечем. skrepka не выбирает копию и не запирает документ: она отклоняет правки только в тех местах, где комментарий мог бы находиться, а остальной документ правится как обычно. Раньше такой документ вставал целиком. Сами копии при этом править нельзя ничем: цитата внутри повторённого абзаца не уникальна ни при каком удлинении, поэтому обхода внутри skrepka не существует — отказ говорит об этом прямо и не советует гадать. Разводится одним словом: как только тексты копий перестают совпадать, всё правится обычным порядком.

**Абзац со смарт-чипом или ссылкой-карточкой.** Текста такого абзаца API не отдаёт, поэтому skrepka считает его возможным местом комментария и отклоняет правки в нём. Проверка включается только там, где путаница вообще возможна — когда в прокомментированном абзаце есть ссылочное содержимое, — поэтому обычная строка со смарт-чипом (их вставляет, например, шаблон «Заметки со встречи») документу не мешает. Уберите чип в интерфейсе, и абзац правится как обычный.

**Комментарий на сноске или в колонтитуле** правкам не мешает: его якорь лежит вне тела документа, и добраться до него правка текста не может.

**Закрытый тред теряет защиту своего фрагмента.** Google не отдаёт закрытые треды в экспорте, поэтому skrepka не знает, где стоял их якорь, и это место не защищает. Для замены текста это безопасно: замерено, что тред не пропадает, после переоткрытия возвращается живым, но оказывается привязан к новому тексту, к которому изначально не относился. А вот удаление фрагмента закрытый тред не переживает, и это не вероятность, а замеренный факт: если абзац, на котором висел закрытый тред, переписан, тред исчезает совсем — его нет ни в тексте, ни на полях, ни в списке решённых, и переоткрытие его не возвращает. В API он при этом продолжает числиться живым, так что по ответу команды этого не увидеть. Перезапись прокомментированного фрагмента (`patch`) устроена мягче: удаление в ней — ровно один символ, и замерено на худшем случае (закрытый тред, чей весь якорь и есть этот символ), что тред при этом остаётся в списке решённых с пометкой Google «Исходный контент удален» — теряет привязку, но не слова. `sync` правит текст удалением целых абзацев, поэтому при закрытых тредах он предупреждает и работает дальше, а не отказывает: разговор в закрытом треде окончен, и остановленный документ обходится дороже. Перед правкой skrepka выгружает содержимое всех закрытых тредов в файл рядом с вашим `.md` — слова сохранятся, хотя привязка к месту будет потеряна, — и отдельно называет те треды, которые по её оценке стояли как раз в переписываемых абзацах. Архив накапливает не только сами треды, но и ответы внутри них: если ответ позже удалили в Google, его прежняя архивная копия не исчезнет при следующем `sync`. Оценка места приблизительная: тред ищется по своей устаревшей цитате, и если такой текст встречается в документе несколько раз, в архиве так и сказано — «одно из N мест», а не «здесь». Если комментарий важно сохранить на месте, не закрывайте тред до того, как текст доправлен.

**Непринятые правки-предложения (tracked changes).** Точечные правки через `patch` работают на документе с предложениями: отклоняется только та операция, которая задевает само предложение. Что происходит при замене поверх предложенного текста, никто не мерил, поэтому туда skrepka не лезет. Синхронизация (`sync`) при непринятых предложениях по-прежнему останавливается целиком: она сверяет весь документ с локальным файлом. Решение в обоих случаях — принять или отклонить предложения в интерфейсе Google Docs.

**skrepka защищает треды, а не каждый якорь по отдельности.** Один комментарий можно повесить сразу на несколько фрагментов. Инструмент гарантирует, что тред не превратится в призрака, то есть что хотя бы один его фрагмент уцелеет, — но не гарантирует сохранность каждого из них по отдельности.

**Отказ считается по операции, а не по документу.** Если в одном `ops.json` десять правок и одна из них упирается в живой якорь, остальные девять применяются, а отклонённая называется отдельно в ответе. С 0.12 это верно и для проверок, которые идут до записи: неуникальная цитата, ненайденный текст или пересечение двух правок между собой отклоняют свои операции, а не файл целиком (пересекающаяся пара отклоняется вдвоём — применение любой из них сдвинуло бы цель другой). Останавливается всё только тогда, когда состояние документа перестаёт быть известным, — например, если связь оборвалась после отправки правки.

**Правки, зависящие друг от друга, проходят одним вызовом.** Если первая правка делает цитату второй уникальной, второй достаточно дождаться своей очереди: на документе с комментариями операции применяются последовательно, каждая по свежему чтению. Такая операция помечена в квитанции — проверку на пересечение с остальными правками она не проходила, потому что на момент проверки её цель ещё не читалась однозначно. На документе без комментариев все правки уезжают одним неделимым пакетом, повторного чтения там нет, и зависимая правка отклоняется — разнесите её на два вызова.

**Серия быстрых ответов больше не блокирует документ.** Раньше два ответа, отправленные в одну и ту же секунду, делали учёт комментариев неразрешимым и останавливали все замены до тех пор, пока человек не закроет или не удалит треды. Это исправлено. Остался редкий случай: если у треда вообще нет ни одной секунды, которую не делит с ним чужая запись, опознать его в выгрузке нечем и правки блокируются. Практически это значит, что комментарий создан ровно в ту секунду, в которую агент отвечал в другой тред. Решение — ответить в этот тред: секунда ответа станет его приметой. Отвечать в такие треды нужно по одному, иначе ответы снова совпадут.

**Резолв комментариев делает только человек.** Агент не закрывает треды: по правилам он не вызывает `resolve` вовсе, а без флага `--yes` команда и так отказывает. Полная перезапись документа требует флага `--acknowledge-loss` только при наличии в документе комментариев или именованных диапазонов: документ без тех и других перезаписывается без вопроса. Флаг — это отметка о согласии, а не доказательство: правила требуют от агента сначала спросить вас словами и дождаться явного «да». Спрашивать он обязан, назвав альтернативу: правки в комментированный документ вносит `patch`, и треды при этом остаются живы. Если часть правок `patch` не смог применить, это список мест для вас, а не основание для полной перезаписи.

## Стили и типографика

**Точечный стиль не является Markdown-roundtrip.** `patch` поддерживает
`style_quote`/`style_range` для bold, italic, underline, strikethrough, цвета,
кегля и семейства шрифта. `download --format md` предупреждает о цветах,
подсветке, underline/strike и типографике, которые последующий `sync` не
представит; цвет в Markdown не кодируется. Для `style_range` поле
`occurrence` недопустимо всегда; на комментированном документе оно также
запрещено для `style_quote`, даже со значением `1`.

**Полная перезапись абзаца теряет пёстрое оформление внутри него.** Если в одном абзаце намешаны разные шрифты, кегли или цвета и абзац переписывается целиком, это оформление сбрасывается. skrepka сообщает об этом полем `inline_styles_dropped` в ответе. Ровный, однородный стиль абзаца при этом сохраняется.

**Тонкая типографика при полной перезаписи абзаца.** Неразрывные пробелы и подобные мелочи могут не сохраниться в исходном виде.

**Свойства абзаца сохраняются.** Отступы, выравнивание, межстрочный интервал и фон абзаца остаются на месте, когда меняется только текст внутри абзаца.

## Синхронизация (`sync`)

`sync` остаётся экспериментальной (бета). Поддержанный сценарий по-прежнему другой: ответить на комментарии заказчика и поправить текст на месте через `comments`, `reply` и `patch` — с 0.10.0 `patch` умеет переписать прокомментированный фрагмент целиком, не потеряв тред, а с 0.12 это работает и на документах с закрытыми тредами. Цикл «скачал `.md`, поправил локально, залил обратно» существует как бета и нужен, когда на руках целиком новый текст: он сохраняет открытые треды, но честно отказывает, если новый текст переписывает прокомментированные абзацы — эти абзацы правит `patch`. Чего делать не нужно ни в каком случае: заменять отказ `sync` полной перезаписью через `update` — она уничтожает треды.

## Платформа и доступ

**Только Unix.** Защиты файлового ввода-вывода опираются на механизмы Unix, поэтому Windows в 0.12 не поддержан.

**Нужен свой Google OAuth-клиент.** skrepka не поставляет общий проверенный клиент: вы заводите собственный проект Google Cloud (см. [QUICKSTART.md](QUICKSTART.md)). Почему так и что это значит для приватности, объясняет [PRIVACY.md](../PRIVACY.md).

**Изображения ненадолго становятся публичными** во время вставки, потом доступ снимается. При аварийном сбое картинка может остаться публичной. Подробности в [PRIVACY.md](../PRIVACY.md) и [SECURITY.md](../SECURITY.md).

**Картинки для загрузки должны лежать рядом с `.md`.** skrepka загружает только те изображения, что лежат в каталоге вашего markdown-файла или в его подкаталогах. Абсолютный путь, выход через `../` и симлинк за пределы дерева она отклонит и оставит ссылку в тексте как есть. Причина: markdown может быть выгрузкой документа, который писали посторонние, и такая ссылка иначе отправила бы в Drive произвольный файл с вашего диска.

**SVG не загружается.** Принимаются только растровые форматы: PNG, JPEG, GIF, WebP, BMP, TIFF. SVG — это документ, а не картинка: он умеет ссылаться на внешние адреса и на локальные файлы, и рендерер такие ссылки послушно откроет. Вместо того чтобы рендерить SVG без песочницы, skrepka отказывается от него совсем. Конвертируйте в PNG сами.
